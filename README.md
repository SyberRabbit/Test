## 0. 先给结论（相对初版的修正）

**不是机房把这台机器搞挂了，也不是 Hy2 那 101 个端口被逐个静态封死，更不是 VPS 没在听。**

是出口侧（公司移动网 / 移动骨干 / GFW，客户端分不到哪一层）按 **「你正在用的那条代理流」** 动态掐：

- 用节点 1 → 节点 1 的 TCP 443 用一段时间后 `i/o timeout`；此时节点 4 往往还能通
- 用节点 4 → 节点 4 的 Hy2 用一段时间后 `context deadline exceeded`（出包有、回包无）；此时节点 1 往往还能通
- 一切走，被掐的那条过一会儿自己恢复
- 空闲 delay 测试经常是绿的，所以「现在测一下端口」会误判成「没封」

这是猫鼠，不是「协议第一包就被写死」。但已经能把 **同 IP 上两条不同协议** 分开处理，多端口 hopping 帮不上忙。

## 一、初版在问什么（2026-09-06 左右，节点 1 Reality）

当时只盯着节点 1。故障期大约 6～7 分钟，然后自己好。

同一时刻，对同一台 `A.A.A.A`：

| 检测项 | 故障节点 A | 对照节点 B |
|---|---|---|
| ICMP ping | 5/5 通，0% 丢包，158ms，TTL 46 | 3/3 通，154ms |
| TCP 443 | 连续 5 次 `Operation timed out` | 成功 |
| TCP 80 | 超时 | `Connection refused`（有 RST） |
| TCP 22 / 8080 | 超时 | — |

读法当时是：

1. A 的 **所有 TCP 端口一律超时、连 RST 都没有** → 不像「只墙 443」，像整个 IP 的 TCP 被黑洞
2. B 的 80 能回 RST → 本机 TCP 栈正常
3. ping 158ms、抖动 0.73ms、0% 丢包 → 链路质量没问题，坏的是「TCP 可达性」
4. SYN 空等 10 秒，一个字节都没有

mihomo 故障期内只有这一个出口 IP 报错，直连国内正常，没有 TLS / Reality handshake 类错误 → **SYN 阶段就失败，TLS 从未开始**。`nc` 绕过 Clash 同样超时。

## 二、今天补了什么（2026-09-15，重点看 Hy2 多端口）

用户原问：节点 1 和 4 同机，公司移动网被间歇掐。**先查 Hy2 多端口：这 101 个端口全被掐了，还是 IP 封了？**

随后纠正了两个误判路径：

1. 空闲探测看到 Reality 通、Hy2 超时，不能说「端口没在听 / IP 封了」——因为 **没用的那条会是绿的**
2. UDP 脏包对 Hy2+salamander 本来就没回包，**超时 ≠ 端口封了**

真实模型用户已经说清楚：

> 用节点 1，节点 1 超时、节点 4 正常；用节点 4，节点 4 超时、节点 1 正常。猫和老鼠。

### 2.1 节点配置（脱敏后仍保留结构）

```yaml
- name: 1 美国Los |自建
  type: vless
  server: A.A.A.A
  port: 443
  network: tcp
  tls: true
  flow: xtls-rprx-vision
  servername: <自己的域名>
  client-fingerprint: chrome
  reality-opts: { public-key: <omitted>, short-id: <omitted> }

- name: 4 美国los |Hy2移动|自建
  type: hysteria2
  server: A.A.A.A
  port: 31219
  ports: 54300-54400
  sni: <同一域名>
  alpn: [h3]
  client-fingerprint: chrome
  obfs: salamander
  # password / obfs-password omitted
```

补充：该域名 A 记录就是 `A.A.A.A`。直连 `https://<域名>/` 能拿到 nginx 200、Let's Encrypt（ISRG Root X2）、TLS1.3。也就是说 Reality 的 dest 是 **自己的站**，不是 `www.sony.com` 那种大站（节点 2 才是 Sony）。

### 2.2 今天上午的空闲快照（09:41 前后，当时正在用节点 4）

出口确认是北京移动 `117.133.151.135`。Clash 选中：`自建-节点组` → `4 美国los |Hy2移动|自建`。

Clash delay（`http://www.gstatic.com/generate_204`）：

| 轮次 | 节点 1 Reality | 节点 4 Hy2 |
|---|---|---|
| 1 | 158ms / 159ms | **504 Gateway Timeout（5s / 8s）** |
| 2 | 156ms | 504 |
| 3 | 156ms | 504 |

节点 2（另一台 Reality / Sony）当时 delay **202ms**，正常。

TCP / ICMP（当时）：

| 探测 | 结果 |
|---|---|
| TCP `A.A.A.A:443` | **OK ~155ms**（所以 IP 没封、Reality 空闲是活的） |
| TCP 80 / 22 / 31219 / 54300 / 54350 / 54400 | 全超时（Hy2 本来就不听 TCP，这条只说明别用 TCP 去扫 UDP 口） |
| ICMP 3 包 | 2 通 1 丢，~157ms，TTL 46 |

Clash connections 里走节点 4 的几条：`upload` 几百～1.8KB，`download` **全是 0**。内核一直在 match 到 Hy2，随后 `context deadline exceeded`。形态是 **客户端有出包，回包没有**。

### 2.3 UDP 脏包扫描：不能当「端口封了」

对 `A.A.A.A` 发随机 UDP：

- Hy2 主端口 `31219`
- hop 全段 `54300–54400` **101 个**
- 对照：53 / 80 / 443 / 9 / 123 / 40000 / 50000 / 60000 / 65500

**110/110 全部超时，0 个 ICMP unreachable，0 个应用层回应。**

这是预期：salamander 对未认证包静默丢；对端对关闭 UDP 口也经常不回 ICMP。所以「这段端口全超时」**推不出**「这段被 ACL 了」。

对照：本机 UDP 本身是活的——`223.5.5.5:53`、`1.1.1.1:53` DNS 正常（8.8.8.8:53 超时是另一回事）。随机 UDP 打 `1.1.1.1:443` 同样无回包（Cloudflare 也不会理脏 QUIC）。

包大小 12 / 52 / 200 / 512 / 1200 / 1250 / 1400 打 Hy2 口全部超时；同时 1250 字节 UDP traceroute 仍能走到对端边缘。**不是公司网把大包 UDP 丢掉。**

### 2.4 真正有用的路径图：UDP traceroute

小包（52B）和大包（1250B）打 `31219`、`54350`，以及 53/80/443/40000 等无关端口，**路径同一条**：

```text
 1  10.2.151.252          公司网关
 2  10.2.253.217
 3  117.133.151.129       移动城域
 4  117.133.131.153
 5  211.136.88.61 / .65
 6-11 221.183.x / 111.24.x   移动骨干（部分跳 *)
12  223.120.161.6         CMI 国际出口  ~160ms
13  223.120.197.2

...
19  193.41.250.149        对端网络内部，反复出现

```

ICMP traceroute 今天 **第 21 跳能到 `A.A.A.A`，157ms**（初版故障期停在 193.41.250.149 的 `*`）。  
UDP traceroute 无论 Hy2 口还是无关口，都是到 `193.41.250.149` 之后最后一跳没 UDP 回应。

如果是「GFW / 移动把 54300–54400 写进端口黑名单」，包应该在国内几跳就没，而且不该和 53/80/40000 走成同一条路、同样到美国门口。

**结论：hop 范围内不是被逐个静态封端口。出站 UDP 能到对端边缘；Hy2 超时窗口里，死的是「这条 Hy2 流的回包 / 最后一跳」。**

### 2.5 猫鼠被现场抓住：一切走，Hy2 立刻活

约 09:59 把 `自建-节点组` 切到节点 1。10:13 再测：

| 节点 | delay |
|---|---|
| 1 Reality | 155ms |
| **4 Hy2** | **154ms**（几分钟前还是连续 504） |

Hy2 进程、hop 端口、证书，都还在。空闲时协议握手能过。

## 三、用日志把「用谁掐谁」钉死

mihomo service log，按分钟桶。`hy2u` / `n1u` = 日志里 `using` 该节点的次数；`r443` / `n1io` = `A.A.A.A:443 connect error: i/o timeout`；`dead` = `context deadline exceeded`。

### 3.1 节点 1（Reality TCP 443）被掐的窗口

昨天 **18:08–18:12**，约 **420 次** `dial tcp A.A.A.A:443: i/o timeout`：

| 分钟 | hy2u | n1u | r443 |
|---|---|---|---|
| 18:08 | 0 | 0 | 20 |
| 18:09 | 0 | 0 | 64 |
| 18:10 | 0 | 0 | 16 |
| 18:11 | 0 | 7 | 55 |
| 18:12 | **24** | 0 | 55 |
| 18:13 | 9 | 0 | **0** |

18:12 切到 Hy2，Reality 的 443 超时 **下一分钟就停**。这不是整机 TCP 黑洞——Hy2 切过去立刻能 match 成功。

报错和初版同一句式（SYN 阶段失败）：

  error: A.A.A.A:443 connect error: dial tcp A.A.A.A:443: i/o timeout

## 四、现在比较可信的机制（求证）

### 4.1 不是这些

| 假说 | 为什么不像 |
|---|---|
| VPS / Hy2 没在听 | 一切走 delay 立刻恢复；空闲 Reality 一直 155ms |
| IP 被封 | 同 IP 另一条协议还通；ICMP 通 |
| `54300-54400` 被端口黑名单 | traceroute 能到对端边缘；无关 UDP 口同一条路；超时窗口里是整段握手失败，但空闲后整段又都能用 |
| 第一包就能认死 Reality / Hy2 指纹 | 空闲 delay 绿；停用就恢复；要「用一段时间」才掐 |
| 对端机房路由环路（初版主假说） | 环路不该「只掐你正在用的那条协议、闲着的那条完全正常」；也不该 6～7 分钟后自己好、切协议立刻好。`193.41.250.86` 重复更像 traceroute 在对端网上绕，不是根因 |
| 源公网 IP 被 VPS 封 | 同 NAT 出口的 Windows 当时能连；停用后同一源 IP 又能连 |
| 本机 TCP/UDP 栈坏了 | 节点 2 正常；DNS UDP 正常；切协议即恢复 |

### 4.2 比较像：按流的动态干扰（先放行，再画像，再丢回包）

两套独立手法，所以才会用谁掐谁。

**节点 1 Reality / TCP 443**

- 空闲：TCP connect 155ms，像普通 HTTPS
- 使用中：长连接、高双向、多路复用，不像在浏览那个只有几 KB 静态页的 `.xyz`
- dest/SNI 还是自己的域名，A 记录指回自己 → 主动探测、流量画像都比「假扮 Sony」容易
- 掐的形态：SYN 黑洞（`i/o timeout`，无 RST），持续约 4～6 分钟，一切走就停

这更像 **「这个 TLS 会话不像在看这个网站」**，不是端口列表，也还不是「看见 VLESS 就秒杀」。

**节点 4 Hy2 / UDP + salamander + 连续 hop**

- salamander 能挡 QUIC 明文头，所以空闲 delay 能过
- 跑起来之后：长时间、大包、稳定 UDP；还在 **连续 101 口**里跳
- 掐的形态：Clash 出包有、回包无；内核 `deadline exceeded`；hop 范围内换端口也建不起隧道
- UDP traceroute 仍能走到 `193.41.250.149`

这更像认 **「这条 UDP 流 / 这种跳端口行为」**，不是认 54321 这个数字。所以多端口在这场猫鼠里是摆设。

**共同特征**

- 先通一段时间（今天 Hy2 从 09:13 用到 09:35 才成片死；初版 Reality 从 04:44 用到 09:28）
- 中途开始丢（回包 / SYN）
- 停用或换协议后，被掐的那条恢复
- 同 IP 上闲着的另一协议不受影响

客户端分不清是公司网关、移动 DPI，还是跨境 GFW。只能说干扰点至少在 CMI 之后仍能看到对端 TTL-exceeded，而 TCP SYN / Hy2 回包在故障期过不去。

### 4.3 初版几个遗留问题，今天怎么看

1. **`193.41.250.86` 重复是不是环路？**  
   不足以当主因。对端网 traceroute 出现环/重复很常见。主现象是「按协议流掐」，不是「包在机房里转圈转死整机」。

2. **ICMP 全通 + 全端口 TCP 超时还有别的成因吗？**  
   有，而且今天更像：**对这条源-目的的 TCP 做黑洞（丢 SYN 或丢回程），ICMP 放行。** 初版扫到 80/22/8080 也超时，可能是当时已经把 `A.A.A.A` 的 TCP 五元组/主机策略打满；但同一时刻 Hy2 若没在用，并不和 Reality 一起死。今天 09:41 Hy2 正在死的时候，TCP 443 反而是通的——所以「全端口 TCP 超时」不是恒定态，是 Reality 被掐时的快照。

3. **同局域网 Windows 当时能连？**  
   仍然可能是：故障窗口只有几分钟；Windows 已有长连接；或者画像按 **源端口 / 客户端实现 / 流量形态** 而不是按公网 NAT IP。没做同一秒双机对比，这条还是敞着。

4. **开机房工单有用吗？**  
   作为「对端转发坏了」证据变弱了。工单可以问 UDP 最后一跳/回程，但更像出口侧策略。工单里建议附：同 IP 双协议互切时间线、ICMP vs TCP vs UDP traceroute、空闲 delay vs 使用中 delay。

## 五、给网友的可复现实验（比空闲扫端口有用）

空闲 `nc` / 随机 UDP / delay 一次，很容易得出「没封」或「全封」两种相反的错结论。比较有效的是：

1. **固定用节点 1 直到它开始 `A.A.A.A:443 i/o timeout`，立刻 delay 节点 4，不要先切走。** 记录两边 delay、ICMP、TCP 443、UDP traceroute `31219` / `54350`。
2. **再固定用节点 4 直到 `deadline exceeded`，立刻 delay 节点 1**（不要切走）。看 Reality 是否仍绿。今天是绿的。
